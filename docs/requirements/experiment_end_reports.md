# 実験終了報告 要件定義書

作成日: 2026-11-10

状態: 要件定義案。アプリケーション実装・DB変更は未実施。

## 1. 目的

学生が実験終了時に実験器具を確認した上で、TAへ終了を報告できるようにする。

学生は実験番号を選択し、登録済みの実験器具チェック項目をすべてチェックする。全項目の確認が完了した場合に限り「終了報告」ボタンを有効にし、報告できるようにする。

終了報告は授業分析に含めない。

## 2. 確定している要求

| ID | 要求 |
| --- | --- |
| END-01 | 学生からTAへ実験終了を知らせる機能を設ける |
| END-02 | 報告前に実験番号を選択する |
| END-03 | 選択した実験番号に登録されている実験器具チェック項目を表示する |
| END-04 | すべての項目にチェックが入るまで終了報告ボタンを無効にする |
| END-05 | 全項目をチェックすると終了報告ボタンを有効にする |
| END-06 | 終了報告を授業分析の対象に含めない |

送信単位、導線、受信後のTA操作、日付制限などは、以下に推奨案を示す。利用者が指定した確定要件とは区別する。

## 3. 現行実装の確認結果

### 3.1 器具項目の設定

`submission.models.ExperimentEquipmentConfig` に、科目/年度と実験番号ごとの器具項目が登録されている。

```text
course_offering + experiment_number → items_json
```

- `course_offering` は科目/年度を識別する。
- `items_json` がチェック項目の一覧。
- admin向けに器具項目の追加・更新・削除・複製処理が存在する。
- 終了報告では、この設定を参照する。学生向けの別の器具項目マスターは作らない。

### 3.2 教員側の既存器具チェック

既存の `ExperimentEquipmentCheckState` と `ExperimentEquipmentCheckLog` は、科目/年度・日付・実験番号・開始時/終了時の単位で管理されている。

これらのチェック状態には班番号・実験曜日による区別がない。学生の班ごとの終了報告を直接保存すると、他班や教員の確認状態を上書きする可能性がある。

そのため、共用するのは器具項目の設定だけとし、学生の確認結果は終了報告用データに保存する。

### 3.3 質問・呼び出しと通知

- `attendance.models.ExperimentHelpTicket` が質問・呼び出しを管理している。
- 実験曜日、班番号、実験番号、対応状態などを記録している。
- 質問・呼び出しの通知は、担当科目/年度のteacherとadminが処理する構成。
- 質問・呼び出しには、同じ科目/年度・曜日・班の未対応チケットによる送信制限がある。
- 授業分析の総件数などは、質問・呼び出しのチケット集合から集計している。

終了報告を既存チケットの種別追加だけで実装すると、送信制限や分析件数に混ざるおそれがある。

## 4. 推奨する構成

- 終了報告用の独立したモデルを追加する。
- 器具項目は `ExperimentEquipmentConfig` から取得する。
- 通知欄は既存の仕組みを拡張して利用し、通知種別を「実験終了報告」として区別する。
- 質問・呼び出しの未対応判定、対応分類、履歴、授業分析とは分離する。
- migrationで新規モデル・一意制約を追加する。既存データの終了報告への変換は行わない。

モデル名・API名は仮称とし、実装時に既存の命名へ合わせる。

## 5. 学生側の操作

### 5.1 導線の推奨案

学生ダッシュボードの科目/年度選択欄付近に「実験終了報告」ボタンを追加し、モーダルを開く。

- ダッシュボードで選択中の科目/年度を引き継ぐ。
- 学生が登録されている科目/年度のみ利用可能とする。
- 表示する曜日・班番号は、その科目/年度の `Enrollment` から取得する。
- モーダルに科目/年度・実験曜日・班番号を明示し、取り違えを防ぐ。
- バーガーメニューにも導線を設けるかは未確定。

### 5.2 基本フロー

1. 「実験終了報告」を押す。
2. 科目/年度・曜日・班番号を確認する。
3. 実験番号を選択する。
4. 対象の器具チェック項目を読み込む。
5. 各項目をチェックする。
6. 全項目のチェックが完了すると「終了報告」が有効になる。
7. 「終了報告」を押す。
8. サーバで検証・保存し、TA側の通知に反映する。
9. 学生側に送信完了と報告状態を表示する。

実験番号の候補は、その科目に登録されている実験番号とする。器具設定のない実験番号も状況を確認できるようにし、送信はできない表示にする。

### 5.3 チェック項目の表示

- 選択した科目/年度・実験番号の登録項目を、設定順に表示する。
- 項目名をそのまま表示し、終了時の確認項目として学生に案内する。
- チェックは初期状態ではすべて未チェックとする。
- 既存の教員用チェック状態から、学生のチェックを自動入力しない。
- 「確認済み 2 / 5項目」のように進捗を表示する。
- 項目名が長い場合も全文を確認できるようにする。
- 実験番号・科目/年度を変更した場合は、古いチェック状態を引き継がない。
- 初期実装では「すべてチェック」ボタンを設けず、項目ごとの操作を基本とする。

### 5.4 終了報告ボタンの有効条件

次のすべてを満たす場合だけ有効とする。

- 有効な学生の科目/年度への所属がある。
- 実験曜日と班番号が設定されている。
- 有効な実験番号が選択されている。
- 器具項目の取得が完了している。
- 器具項目が1件以上存在する。
- 取得したすべての項目にチェックが入っている。
- 同一単位の報告を重複送信しようとしていない。
- 通信・送信処理中ではない。
- 採用した日付・授業日の送信条件を満たしている。

項目が0件の場合に「すべてチェック済み」と判定して送信を許可してはならない。

## 6. 報告単位・日付の推奨案

### 6.1 班の代表者による報告

推奨は、班の代表者1名が報告する方式。

```text
科目/年度 + 実施日 + 実験曜日 + 班番号 + 実験番号
```

- 送信者のユーザIDも記録する。
- 同じ班員が同時に押しても、同じ報告は1件だけ保存する。
- 火曜01班と木曜01班は別の報告単位とする。
- 同じ班・実験番号でも、実施日が違えば別の報告単位とする。
- 質問や呼び出しが未対応でも終了報告は送信できる。
- 終了報告が未確認でも、質問や呼び出しの送信を妨げない。
- 他班員がすでに送信している場合は「この班は報告済み」と状態を表示する。不要な個人情報は返さない。

全学生が個別に報告する方式にする場合は、重複判定と閲覧範囲を学生単位に変更する必要がある。実装前に確定する。

### 6.2 日付の扱い

- 日付・時刻の基準は `Asia/Tokyo` とする。
- 実施日はサーバで決める。ブラウザから任意の過去日付を指定して登録できないようにする。
- 学生からの新規報告は当日分に限る方式を推奨する。
- TAは未確認の報告を翌日以降も確認できる方式を推奨する。
- 送信日が変わった場合は、古いモーダルをそのまま送信せず再読込を求める。
- 授業予定日・実験曜日との一致を必須にするか、補講日をどう扱うかは未確定。
- 出席打刻済みであることを送信条件に含めるかも未確定。

## 7. TA側の受信・確認

### 7.1 通知先の推奨案

| ロール | 新規報告 | 通知・一覧閲覧 | 対応状態の更新 |
| --- | --- | --- | --- |
| student | 自身の所属科目/年度から送信 | 自身の報告、同一班の重複確認に必要な最小限の状態 | 不可 |
| teacher（TA） | 不可 | 担当科目/年度のみ | 担当科目/年度のみ |
| admin | 不可 | 管理対象の全報告 | 可能 |
| course-teacher | 不可 | 登録科目/年度の閲覧のみを推奨 | 初期案では不可 |
| non-editing teacher | 不可 | 初期案では対象外 | 不可 |

teacherをTAとして扱う。通知先にcourse-teacherを含めるか、TA不在時の運用をどうするかは実装前に確定する。

### 7.2 通知内容

- 種別: 実験終了報告。
- 科目/年度、実施日、実験曜日、班番号、実験番号。
- 報告日時と状態。
- 教員側の詳細表示では、送信者の学籍番号・氏名、報告時の器具項目と確認結果を表示する。
- 質問・呼び出しと取り違えない表示にする。
- 既存の定期更新と手動再読込を利用する。メール・音声・ブラウザプッシュ通知は初期案に含めない。

### 7.3 状態の推奨案

```text
未確認 → 確認中 → 確認済み
```

- TAは未確認から直接確認済みへ変更することもできる。
- 状態の変更者・変更日時を記録する。
- 更新競合により、確認済みの報告が古い操作で未確認へ戻らないようにする。
- 状態を戻す操作、学生による取消、差戻し・再報告は初期案に含めず、必要性を確認する。
- 終了報告の確認に、質問・呼び出し用の「対応分類」を要求しない。
- 通知を開いたことと、実験終了を確認済みにすることは区別する。

未確認・確認中は日付をまたいでもTAが一覧で操作可能とする。確認済みは当日分を通知に表示し、過去分は履歴で確認できる方式を推奨する。

既存の通知表示上限により報告が隠れても対応できるよう、TA側に終了報告の一覧導線を設け、未確認分をページ送り等で全件確認できるようにする。通知件数・バッジの上限や他種別との優先順位は実装前に決める。

## 8. 保存するデータ

独立モデル `ExperimentEndReport`（仮称）を新設する案とする。

| 項目 | 内容 |
| --- | --- |
| reporter | 報告した学生のUser ID |
| course_offering | 科目/年度 |
| report_date | 実施日。サーバで確定 |
| experiment_day | 報告時点の所属実験曜日 |
| experiment_group | 報告時点の所属班番号 |
| experiment_number | 選択した実験番号 |
| equipment_config | 参照した器具設定。削除されても報告履歴を保持できる構成 |
| equipment_version | チェックに使った項目一覧を識別するバージョン情報 |
| equipment_items_snapshot | 報告時点の器具項目一覧 |
| checked_items_snapshot | 報告時にチェックされた項目 |
| status | 未確認・確認中・確認済み |
| created_at / updated_at | 報告・更新日時 |
| handled_by / confirmed_at | 対応者・確認完了日時 |

- 日付・曜日・班番号・器具項目は報告時点の値を保持する。
- 後から所属や器具設定が変わっても、過去の報告内容を変えない。
- 器具設定の削除が終了報告の削除につながらないようにする。
- 班単位方式では、科目/年度・実施日・曜日・班番号・実験番号にDBの一意制約を設ける。
- 状態変更履歴を別モデルに保存するかは、必要な監査範囲に応じて確定する。

## 9. サーバ側の検証と二重送信対策

- 学生のユーザIDはログイン情報から確定し、リクエスト内の別ユーザIDを信用しない。
- 科目/年度へのstudentとしての所属を確認する。
- 曜日・班番号はサーバが `Enrollment` から取得する。
- 実験番号が対象科目の登録値であることを確認する。
- 対象の器具設定が存在し、項目が1件以上あることを確認する。
- クライアントが送った件数や「全チェック済み」フラグだけで判定しない。
- 登録項目と送信されたチェック項目を照合し、不足・不正項目を検出する。
- 取得時の器具設定バージョンと送信時の設定が異なる場合は、再読込・再確認を求める。
- 重複項目を送ることで必要件数を満たしたように見せられないようにする。
- 保存はトランザクションとDB制約で保護し、同時送信でも重複レコードを作らない。
- 通信失敗後に再送された場合も、既存の報告状態を返すなどして二重登録を避ける。
- 送信開始時にボタンを無効にし「報告中…」と表示する。
- 成功時はモーダルを閉じて送信済み状態を反映する。モーダルを閉じない設計を採用する場合も再送ボタンは有効にしない。
- 失敗時はチェック内容を保ち、エラーの内容に応じて再試行・再読込できるようにする。

## 10. 器具設定がない・変更された場合

| 状況 | 動作 |
| --- | --- |
| 実験番号未選択 | 器具項目は表示せず、報告不可 |
| 項目読込中 | 読込中と表示し、報告不可 |
| 器具設定なし | 設定がない旨を表示し、報告不可 |
| 項目0件 | 項目未登録と表示し、報告不可 |
| 一部のみチェック | 未確認項目が分かる表示にし、報告不可 |
| 全項目チェック | 他条件を満たす場合のみ報告可能 |
| チェック後に器具設定更新・削除 | サーバで送信を受理せず、最新項目の再確認を求める |
| 実験番号変更 | チェックをリセットして再取得 |
| 班員が先に報告済み | 重複登録せず、報告済み状態を表示 |

## 11. 授業分析・既存業務との境界

終了報告は授業分析に含めない。独立モデルに保存し、次を保証する。

- 質問・呼び出しの総件数を増やさない。
- 種別比率、対応分類別、時間帯別、授業回数別、実験項目別、対応者別、班番号別の各集計に含めない。
- 質問・呼び出しの対応完了時間にも含めない。
- 質問・呼び出し履歴へ、終了報告を混在させない。
- 既存の教員用器具チェック状態・履歴を学生の報告で更新しない。
- 終了報告・TA確認によって、出席・退室打刻、遅刻・欠席、実験時間の加減点を変更しない。
- 終了報告・TA確認によって、例題進捗、`ExperimentCompletion`、レポート受付・成績を自動更新しない。

とくに既存の自動受付処理は実験完了・進捗を参照するため、終了報告を実験完了フラグへ直接連動させない。

将来「TA確認後に実験完了へ連動する」等を追加する場合は、独立した仕様として承認・テストする。

## 12. API・権限・安全性

APIは、初期情報取得、報告送信、TA向け一覧・詳細取得、状態更新を分ける。

```text
GET  終了報告の初期情報・器具項目
POST 終了報告を送信
GET  終了報告の一覧・詳細
POST TAによる状態更新
```

- GETでは報告や確認状態を変更しない。
- POSTには認証・CSRF・ロール・対象科目/年度の権限チェックを適用する。
- report IDだけを指定して、他科目/年度の内容を閲覧・更新できないようにする。
- role別のserializerを用意し、画面で隠すだけの情報制御にしない。
- 学生へTA用の内部情報・不要な他学生の個人情報を返さない。
- 器具項目はテキストとして表示し、HTMLやJavaScriptとして実行しない。
- 複数班員による同時操作、古い画面からの送信、繰り返し送信を考慮する。
- ログには報告ID・操作者ID・対象科目/年度・状態・日時を記録し、個人情報を無制限に出力しない。

## 13. UI・表示要件

- ライトモード・ダークモードの両方に対応する。
- モーダルはヘッダー・フッターに隠れない位置・高さとする。
- 項目が多い場合はモーダル内でスクロールできるようにする。
- PC・スマートフォンで項目名とチェックボックスを操作できるようにする。
- キーボード操作とチェックボックスのラベルクリックに対応する。
- 完了数・未チェック理由・通信状態・送信結果を文字でも表示する。
- 自己申告のチェック完了と、TAによる実物確認を同じ意味で表示しない。

## 14. 受入条件・テスト項目

1. 学生が実験番号を選ぶと、対象科目/年度・実験番号の登録器具項目だけが表示される。
2. 初期状態では全項目が未チェックで、報告ボタンが無効である。
3. 1項目でも未チェックなら報告ボタンが無効で、全チェック時に有効になる。
4. チェックを外すと直ちに報告ボタンが無効へ戻る。
5. 実験番号・科目/年度を変更すると、古いチェック状態が引き継がれない。
6. 器具設定なし・項目0件・通信失敗時に送信できない。
7. フロントの無効化を回避した直接POSTでも、未チェック・不正項目を含む報告が拒否される。
8. モーダル表示後の器具項目変更・削除を検出し、再確認を求める。
9. 学生が送信すると、対象のTAが通知・詳細を確認できる。
10. 別科目/年度のTA、未ログイン利用者、権限外ロールが閲覧・更新できない。
11. 学生が別人・別班のIDを送っても報告主体を偽装できない。
12. 火曜と木曜の同一班番号が互いの報告を妨げない。
13. 質問・呼び出しの未対応状態が終了報告を妨げず、終了報告も質問・呼び出しを妨げない。
14. 連打・同時送信・通信失敗後の再送でも重複報告が作成されない。
15. 器具設定・所属を後日変更しても、保存済み報告の項目・曜日・班が変わらない。
16. 未確認の終了報告が通知件数上限や日付変更で操作不能にならない。
17. TAによる状態更新で、操作者・確認日時を記録できる。
18. 終了報告を作成・更新しても、授業分析の全チャート・総件数が変わらない。
19. 既存の教員用器具チェック、実験進捗、出席・退室、加減点、レポート受付状態が変わらない。
20. CSRF、不正なJSON、未登録実験番号、不正な項目、HTML相当の項目文字列を安全に扱える。
21. PC・スマートフォン・ダークモードで、モーダルと全項目を操作できる。

実装時には、送信可否・差分設定検証・権限・重複送信・授業分析への非混入を単体テストで検証する。画面操作と同時送信は結合テストでも確認する。

## 15. 実装前に確定する事項

| 項目 | 推奨案 |
| --- | --- |
| 送信単位 | 班の代表者1名が、当日・実験番号ごとに1件報告 |
| 学生側の導線 | 学生ダッシュボードの科目/年度選択付近のボタン |
| 通知・処理担当 | 担当科目/年度のteacher（TA）、admin |
| course-teacher | 登録科目/年度の閲覧のみ。通知対象にするかは要確認 |
| non-editing teacher | 初期対象外 |
| TA側の導線 | 既存通知欄＋未確認報告を全件確認できる一覧 |
| TAの処理状態 | 未確認・確認中・確認済み |
| 学生の送信日 | 当日分のみ。授業日・曜日・打刻条件は要確認 |
| TAの確認日 | 翌日以降も未確認分を操作可能 |
| 取消・差戻し・再報告 | 初期案には含めない |
| 他機能への自動連動 | 行わない |

器具チェックで学生が自己申告できるのは「確認した」という事実であり、実物の片付けや数量が正しいことをシステムが保証するものではない。TAによる実物確認が必要な場合は、確認済みにする運用へ組み込む。

## 16. 実装時の主な確認対象

- `submission/models.py`: 器具項目設定、既存の教員用チェックモデル。
- `submission/views_admin.py`: adminによる器具項目の管理。
- `submission/views_teacher.py`: 既存の器具チェック・保存処理。
- `submission/templates/submission/student_dashboard.html`: 学生側のボタン・報告画面。
- `submission/static/submission/js/student_dashboard.js`: 科目/年度の引継ぎ、チェック・送信制御。
- `attendance/models.py`: 質問・呼び出しモデルと新規終了報告モデルの分離。
- `attendance/views.py`: 通知・権限・詳細・分析集計への影響。
- `submission/templates/submission/header.html`、`submission/static/submission/js/header.js`: 通知表示・TA側の詳細操作。
- 関連URL定義、migration、role別serializer、単体・結合テスト。
