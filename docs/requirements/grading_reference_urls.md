# 添削画面の参考文献URL保存・差分表示 実装要件

作成日: 2026-11-10

状態: 2026-11-10 実装。改行URL対応をv2へ更新し、migrationを追加済み。本番DBへの適用・デプロイは未実施。

## 1. 目的

学生が提出したPDFの参考文献からURLを抽出・保存し、教員が添削画面上で確認・コピーできるようにする。

再提出時には以前の提出と比較し、追加されたURLを優先表示する。添削済みPDFを開いた場合も、保存済みの抽出結果を表示する。

URLの抽出・表示だけではリンク先にアクセスしない。URLの存在や参考文献としての妥当性は、教員が必要に応じて確認する。

## 2. 対象範囲

- 主対象は `grading_form` の本レポート添削。
- 同画面で開く添削済みの本レポートも対象。
- 3回目提出の回収時にも、その提出のURLを記録する。
- 学生向けダッシュボードへのURL一覧追加は今回の対象外。
- `final_grading_form` でも同じURL欄を表示する。
- PDF本文の自由選択・コピーやOCRは、今回の機能には含めない。

## 3. 想定する提出プロセス

| 段階 | URL抽出・保存 | 添削画面の表示 |
| --- | --- | --- |
| 1回目提出 → 初回添削 | 添削を書き込む前に参考文献を解析し、その提出の全URLを保存 | 全URLを表示。初回として扱う |
| 2回目提出 → 初回添削 | 新しい提出PDFを解析し、その提出の全URLを保存。前回と比較 | 前回から追加されたURLを優先表示 |
| 3回目提出 → 回収 | 回収時にも未抽出なら解析対象に登録し、URLを保存 | 後から開いた場合は保存結果を表示 |
| 添削済みファイルを再表示 | 完了済みの抽出結果を利用 | 保存済み一覧・差分を表示 |

「変更されたURLだけを記録する」ためにも、新しい提出の参考文献部分は一度読み取る必要がある。解析を省略できるのは、抽出完了済みの同じ提出を再表示する場合である。

## 4. 提出履歴の単位と提出順

比較対象は以下がすべて一致する `Submission` とする。

```text
student_id + course_offering_id + experiment_number + report_type
```

- 学生の識別には、学籍番号文字列ではなくUserの主キーを使う。
- 本レポートと予習レポートを混ぜない。
- 科目・年度・実験番号・学生が異なる提出とは比較しない。
- 提出順は `submitted_at ASC, id ASC` で確定する。
- `course_offering_id` が空の過去提出は、他科目・年度を推測して比較しない。比較条件が不足していることを表示する。
- 添削を開く順番が提出順と異なっていても、同じ提出履歴から差分を算出する。

## 5. 保存するデータ

推奨は `Submission` と1対1に関連する参考文献URL抽出結果モデルを新設する方式。migrationを伴う。

### 5.1 抽出結果

| 項目 | 内容 |
| --- | --- |
| submission | 対象の提出レコード |
| status | 未実行、処理中、完了、失敗、文字情報なし |
| extraction_scope | 参考文献部分、PDF全体の候補、対象範囲を特定できず |
| source_kind | 提出PDFから抽出、既存の添削済みPDFから後日抽出 |
| urls | その提出に含まれる全URLと掲載情報 |
| extracted_at | 抽出完了日時 |
| extractor_version | 抽出処理のバージョン |
| source_fingerprint | 抽出に使ったファイルの識別情報 |
| error_code | 失敗理由を識別するコード |

### 5.2 URLごとの情報

- PDFから抽出した原文。
- 比較用の正規化キー。
- 掲載ページ。複数ページに同じURLがある場合は全掲載箇所。
- 抽出元が本文文字列か、PDFのリンク情報か。
- PDFの表示文字列と実際のリンク先が異なる場合は、その両方。
- 構文検証結果、画面から開けるか、開けない場合の理由。
- 改行結合などで補正した場合は、その内容と確認が必要であること。

### 5.3 保存方針

- 差分だけではなく、提出ごとの全URL一覧を保存する。
- 過去提出のURLを、新しい提出の抽出結果へ追記して混ぜない。
- 過去のURLは、その提出に関連付けて履歴として保持する。
- 成功済みの結果も明示的に再抽出できる。再抽出前の結果は専用の履歴モデルへ退避し、同じ内容の重複保存を避ける。
- 元PDFの複製や、PDF本文全体の追加保存は行わない。
- 差分は保存済みの提出別一覧から算出できる構造を基本とする。差分も保存する場合は比較元の提出IDを記録する。
- 空一覧で抽出完了した場合と、未実行・失敗・文字情報なしを区別する。

## 6. 抽出方法

- 既存のPyMuPDFによるPDF文字抽出処理を調査し、利用できる部分を共用する。
- コピペチェック向けに空白や文字を正規化した本文は、そのままURL抽出へ使わない。
- 「参考文献」「引用文献」「References」などの見出しを検出し、対応する範囲を優先して抽出する。
- 参考文献の範囲を特定できない場合は、PDF全体のURLを候補として表示し、参考文献として確定した結果と区別する。
- 見出しからPDF末尾まですべて参考文献と決めつけず、後続の節や付録も考慮する。
- PDFに埋め込まれたリンク先情報も候補として取得する。参考文献部分にあるかどうかを区別する。
- 同一提出内の重複URLはまとめ、掲載ページ・抽出元情報を保持する。
- 改行や折り返しを補正する場合は、別の参考文献まで連結しない。
- v2では複数行・字下げ・ホスト名途中・数字のみの継続行・日本語パス・ページ境界を扱い、継続行末の閲覧日を分離する。
- 同じ掲載位置に完全な埋め込みリンクがある場合は、そのリンク情報を優先し、途中までの文字列との重複を避ける。同じ行の別のURLは消さない。
- 判断が曖昧な復元候補やPDFの表示文字とリンク先が異なる場合は、確認が必要な情報として表示する。
- スキャン画像内のURLは初期実装ではOCRしない。文字情報がない場合は、その旨を表示する。
- PDFのJavaScript、外部リンク、添付ファイル、埋め込み実行機能は実行しない。

## 7. 差分判定

前回提出と今回提出のURL集合を比較する。

| 区分 | 条件 |
| --- | --- |
| 初回 | 比較する過去提出がない |
| 追加 | 今回に存在し、前回に存在しない |
| 継続 | 今回・前回の両方に存在する |
| 削除 | 前回に存在し、今回に存在しない |

例:

```text
1回目: URL-A、URL-B
2回目: URL-B、URL-C

追加: URL-C
継続: URL-B
削除: URL-A
```

- URLが変更された場合は、原則として旧URLの削除と新URLの追加として扱う。
- 一度削除されて再登場したURLは、直前の提出との差分では追加として扱い、過去の掲載履歴も確認できるようにする。
- 前回提出が未抽出なら、先に抽出するか比較待ちとして扱う。未抽出・失敗を空一覧として比較しない。
- 比較元と今回の抽出バージョンが異なる場合も差分を確定しない。再抽出時には比較に必要な旧バージョンの提出も更新する。
- URLが同じままリンク先のページ内容が更新された場合は検出対象外。

### 比較用の正規化

- 原文を保持した上で、別の比較用キーを作る。
- スキーム・ホスト名の大小文字など、同値と判断できる範囲だけを正規化する。
- パスやクエリの大小文字、クエリ項目、フラグメントを一律に削除・変更しない。
- `http` と `https`、末尾スラッシュの有無を無条件で同一扱いしない。
- URL全体へのNFKC変換や、途中の空白・記号の無条件削除は行わない。
- 推測して修復したURLを、確認済みの原文として上書きしない。

## 8. 抽出の実行と再利用

- 初回添削表示時に未抽出であれば、添削内容の保存前に抽出する。
- 添削画面からの抽出要求は、採点保存とは独立した処理とする。
- 3回目の回収については、自動受付・手動受付の双方の経路で抽出漏れがないようにする。
- 抽出失敗で採点画面・採点保存・回収処理を失敗させない。
- 抽出中・失敗・再試行可能な状態を画面で確認できるようにする。
- 同じ提出を複数人が開いても、抽出レコードやURLが重複しないようにする。
- 処理中のまま残った場合の再試行方法を設ける。
- 添削保存によるファイル名変更やハッシュ変更だけでは、保存済みURLを無効化しない。
- 学生の提出PDF自体が差し替わった場合は、抽出結果を無効化し、新しいファイルを対象に再抽出する。
- 関連する実験番号・レポート種別・科目年度が修正された場合は、比較する提出履歴も再評価する。
- 通常の再表示では、抽出のためにPDF全体を毎回読み直さない。
- 既存の添削済みPDFから後日抽出した場合は、その出所を記録する。教員の追記URLを含む可能性を明示し、提出原文から抽出済みとは扱わない。
- PDF差し替えとURL抽出が同時に走った場合は、古いファイルの抽出結果を新しい提出内容の結果として確定しない。

実行方式は既存構成に合わせて決める。バックグラウンド処理を採用する場合は、新たな常駐サービスの要否も実装前に明示する。

## 9. 添削画面のUI

- 画面上部に折りたたみ可能な「参考文献URL」欄を配置する。
- 1回目は全URL、2回目以降は追加URLを優先表示する。
- 「追加URL」「現在の全URL」「過去の履歴」を切り替えられるようにする。
- 追加URLが0件なら、その旨を表示する。現在の全URLは引き続き閲覧可能とする。
- URLごとに掲載ページと、初めて登場した提出回を表示する。
- 各URLに「コピー」を配置し、成功・失敗が分かるようにする。
- クリップボードAPIを使えない環境でも、文字列を選択してコピーできるようにする。
- 開く条件を満たすURLだけに「別タブで開く」を提供する。
- 長いURLは表示を折り返せるようにし、コピー時は省略されていない文字列を使う。
- 一覧の高さに上限を設け、PDFの表示領域を過度に圧迫しない。
- 添削済みファイルでも保存済み一覧を表示する。
- PDFの倍率変更・添削ツール切替・採点保存から独立して操作できるようにする。

## 10. セキュリティ要件

### 10.1 URLへの自動アクセスを禁止する

- 抽出・保存・差分計算・一覧表示の過程でリンク先へ通信しない。
- HTTPのGET/HEADによる存在確認を自動実行しない。
- サムネイル、favicon、外部画像、リンク先タイトルを取得しない。
- 短縮URLの展開やリダイレクト先の追跡をしない。
- URL判定のためだけにDNS問い合わせを発生させない。
- URLを外部の危険サイト判定サービスへ自動送信しない。
- 外部サイトへのアクセスは、利用者が明示的に「開く」を選んだ場合に限定する。

この設計で、抽出URLを利用したサーバ側の任意アクセス機能を持たせない。

### 10.2 表示する文字列を実行しない

- 抽出文字列を信頼しない。
- Vueの通常の文字列表示、`v-text` または安全なテキスト出力を使用する。
- 抽出結果を `v-html`、`innerHTML`、スクリプト、CSSとして挿入しない。
- HTMLの属性へ設定する場合も、URL検証と適切なエスケープを行う。
- DBに保存済みであることを理由に、URLを信頼済みとして扱わない。

### 10.3 コピーとリンクを開く操作を分ける

- 原文は確認・コピー用に保持する。疑わしいURLも、リンクとして実行せず文字列として扱う。
- 開けるスキームは、構文検証済みの `http` と `https` に限定する。
- `javascript:`、`data:`、`file:`、`vbscript:` などは開けない。
- スキームのないURLや構文が壊れたURLは、推測でリンク化しない。
- 制御文字、認証情報、判定を混乱させる形式を含むURLは、画面から開けない。
- localhost、内部用ホスト名、プライベート・ループバック・リンクローカル等のIPを明示したURLは開けない。
- IPの判定ではIPv4・IPv6と、URLパーサーが受理する代替表記を考慮する。
- ホスト名が内部IPへ名前解決されるケースや、リンク先のリダイレクトまでは、この通信しない検証では判定できない。
- クライアントへ返すURLの検証状態・開く可否はバックエンド側で決める。フロント側でもスキーム等を確認する。

### 10.4 外部サイトを開く際の対策

- 抽出URLと接続先ホスト名を表示する。
- PDFの表示文字列と実際のリンク先が異なる場合は区別して表示する。
- 別タブで開き、`rel="noopener noreferrer"` を指定する。
- 添削画面内のiframeに外部サイトを埋め込まない。
- 開くボタンの存在やHTTPSであることを「安全確認済み」の意味で表示しない。
- コピー後や別タブで開いた先のマルウェア・フィッシングまで防ぐ機能ではないことを仕様上明確にする。

### 10.5 権限とAPI

- 既存の提出物閲覧権限チェックを適用し、Submission IDの指定だけで他の提出物のURLを取得できないようにする。
- `teacher`、`course-teacher`、`admin` はアクセス権のある提出について閲覧・コピー可能とする。
- `non-editing teacher` も既存の閲覧範囲内で利用できる。採点・受付・提出ファイルの変更権限は追加しない。
- 学生用payloadへ教員向けURL履歴・抽出メタデータを追加しない。
- 抽出開始・再試行などDBへ変更を行うAPIはPOSTとし、認証・提出物アクセス権・CSRF検証を適用する。
- 読み取りAPIと抽出開始APIを分け、画面のGET処理に重い抽出を抱え込まない。
- 閲覧専用ロールによる抽出要求を許可しても、採点・受付・提出ファイルを変更する権限は付与しない。

### 10.6 処理負荷とログ

- PDFサイズ、ページ数、抽出URL数、URL文字数、解析時間に上限を設ける。
- 具体的な上限値は、既存の提出制限と実データを確認して決める。
- 上限超過による一部抽出を、全件抽出完了と同じ表示にしない。
- 壊れたPDFや暗号化PDFを受けても、失敗状態を記録し、通常の添削処理を継続する。
- ログにはSubmission ID、抽出状態、所要時間、件数、エラーコードを記録する。
- URL全文やクエリ内のトークン、PDF本文を通常ログへ無制限に出力しない。

## 11. 既存データへの対応

- migrationでモデル・必要な制約を追加する。
- migration内で全PDFの一括解析は行わない。
- 既存提出は初回利用時に未抽出として扱い、必要な提出だけを解析する。
- 過去データを一括処理する場合は、別の管理コマンド等で実施する。
- 元ファイルが存在しない場合や文字情報が失われている場合は、その状態を表示する。
- 未抽出・失敗・比較不能を「URLの追加なし」と表示しない。

## 12. 実装時の主な確認対象

- `submission/models.py`: Submission、既存の文字抽出結果モデル、新設モデルとの責務。
- `submission/views_grading.py`: 初回添削、添削保存前の抽出、既存文字抽出処理。
- `submission/templates/submission/grading_form.html`: 上部の参考文献URL欄。
- `submission/static/submission/js/grading_form.js`: 抽出状態取得、差分表示、コピー操作。
- `submission/static/submission/css/grading_form.css`: 一覧の高さ・折りたたみ・レスポンシブ表示。
- `submission/access.py`: 既存の提出物アクセス権チェック。
- 提出ファイル差し替え処理、自動受付・手動受付処理、関連URL定義。

## 13. 受入条件

1. 1回目の添削で提出PDFのURLが記録され、コピーできる。
2. 2回目で追加・継続・削除を正しく判定し、追加URLを優先表示する。
3. 同一学生でも科目・年度・実験番号・レポート種別が違えば比較しない。
4. 提出日時が同じ場合もIDで提出順を確定できる。
5. 添削済みファイルを開いても保存結果を表示し、PDFを毎回再抽出しない。
6. 3回目の自動受付・手動受付でもURLを記録できる。
7. 前回未抽出・抽出失敗を空一覧とみなさず、差分未確定と表示する。
8. 同時表示・再試行で抽出データが重複せず、失敗しても添削・回収が継続できる。
9. PDF差し替えでは再抽出し、通常の添削保存では保存済みURLを維持する。
10. スキャンPDF、壊れたPDF、暗号化PDF、URLなし、長いURL、改行されたURLを区別して扱える。
11. 抽出文字列にHTMLやスクリプト相当の内容があっても実行されない。
12. 禁止スキーム、認証情報付きURL、内部宛てを明示したURLを画面から開けない。
13. PDFの表示文字列とリンク先が異なる場合、実際に開くURLを確認できる。
14. 抽出・表示時に外部URL・favicon・短縮URL展開・危険サイト判定サービスへの通信が発生しない。
15. 権限のない利用者がURL一覧の取得・抽出要求を行えない。
16. Chrome・Safariでコピーを確認し、クリップボードAPIが使えなくても選択コピーできる。
17. URL欄の操作がPDF倍率・添削位置・採点保存に影響しない。
18. URL件数・解析時間等の上限超過を検出し、部分的な結果であることが分かる。

## 14. 実装時の決定事項

- `grading_form` と `final_grading_form` で共通のVueコンポーネントを使用する。
- URL欄は操作欄に含め、「操作欄を隠す」と連動する。URL欄自体も折りたたみ可能とする。
- 読み取りはGET、抽出開始・再試行はCSRF検証付きPOSTとする。
- 受付時はSubmissionの保存シグナルからトランザクション確定後にワーカーを起動する。
- ワーカーは `process_reference_urls --submission-id <ID>` 管理コマンド。新たな常駐サービスは追加しない。
- PDF解析はさらに専用子プロセスで実行し、時間・CPU・メモリ制限を設ける。
- 採点保存時に未抽出なら、PDFを書き換える前に制限時間内で抽出する。失敗しても採点保存は継続する。
- ワーカーが停止した場合は90秒で実行権を期限切れとし、次の抽出要求で再試行可能とする。
- 全履歴の解析上限は20提出。上限を超える場合は比較不能と表示し、古い未解析結果を空扱いしない。
- 抽出対象PDFは256MiB、200ページ、URL500件、1URL4096文字、全文200万文字、掲載箇所2000件を上限とする。
- 過去の添削済みファイルには50MiBを超えるものがあるため、v2ではPDFをファイルから直接解析する。学生の新規アップロード容量制限は別に管理する。
- PDF解析子プロセスは実時間15秒、CPU時間10秒、仮想メモリ768MiBに制限する。
- 容量・ページ数・URL件数・URL文字数・実時間上限は `REFERENCE_URL_MAX_BYTES`、`REFERENCE_URL_MAX_PAGES`、`REFERENCE_URL_MAX_COUNT`、`REFERENCE_URL_MAX_LENGTH`、`REFERENCE_URL_TIMEOUT` 設定で変更可能。
- 見出しが見つからない場合はPDF全体の候補として表示する。改行を補正したURLは原文を残し、自動的に開けるリンクにはしない。
- 開くURLのポートは省略・80・443に限定する。
- migrationは `submission/migrations/0045_submission_reference_urls.py`。既存PDFの一括解析は行わない。
- v2では `submission/migrations/0046_reference_url_revisions.py` で抽出結果の履歴モデルを追加する。migration内でPDFの再解析は行わない。

### 反映手順

通常のデプロイでmigrationとcollectstaticを実施する。新しいJavaScriptが静的ファイルmanifestに含まれてからサービスを再起動する。

```bash
./venv_prod/bin/python manage.py migrate --settings=scoring_system.settings_prod
./venv_prod/bin/python manage.py collectstatic --noinput --settings=scoring_system.settings_prod
```

旧方式の成功済み結果を含め、画面の「URLを再抽出」から更新できる。「過去の履歴」では提出ごとに再抽出でき、以前の抽出結果もコピーできる。運用上コマンドから再開する場合も、対象提出IDを明示する。

```bash
./venv_prod/bin/python manage.py process_reference_urls --submission-id <ID> --settings=scoring_system.settings_prod
```

コマンドは処理待ち・期限切れの処理を実行する。失敗済みの結果を再抽出する場合は、画面の再試行操作で処理待ちへ戻す。
